# Languages and translations

English is the default. An explicit `/en/…`, `/bn/…`, or another published locale URL wins over a cookie or account preference. Legacy URLs redirect to a valid saved preference, or English when none exists. Browser language, country, device settings, and IP address never choose the website language. Language and display/settlement currency are separate.

All canonical public language URLs include a prefix, including English. For example, a new visitor opening `/products` is redirected to `/en/products`, even with an Arabic browser language. After selecting Bengali, the equivalent `/bn/products` page renders Bengali; refreshes and locale-aware navigation retain it. Selecting English again saves English. Directly opening a published `/ar/products` would render Arabic and `dir="rtl"` regardless of an English cookie. Unsupported, disabled, or unreadable language variants redirect to the equivalent English URL with their query parameters preserved; they do not render English silently beneath a different language prefix.

The desktop and mobile selectors save an explicit choice in an HttpOnly, SameSite cookie and, when the additive migration and authenticated profile are available, `User.preferredLocale`. A fresh document renders its catalog, selected language, and HTML `lang`/`dir` together. Authentication and existing cart storage are retained. The selector preserves the current pathname, query string, and fragment. Safe drafts for checkout, contact, registration, profile settings, cart choices, and product options are captured in tab-local storage for ten minutes, scoped to the resolved signed-in identity or guest session and consumed once. Passwords, card data, tokens, and files are excluded. In-flight submissions block switching; unsupported rich/admin form edits and sensitive fields produce a warning before leaving. These drafts recover an explicit language switch, rather than promising recovery from arbitrary reloads or browser crashes.

## Implemented coverage and dependencies

The repository contains **2 prepared and configured published interface languages: English (`en`) and Bengali (`bn`)**, with **2,895 required messages per catalog**. The interface audit covers 294 TSX files across storefront, authentication, account, administration, shared components, states, validation, and accessibility text. The original contractual English corpus is retained separately, outside the required translated interface catalog. Runtime administrator publication overrides may reduce the configured list. The native LibreTranslate v1.9.6 installation selects English/Bengali models to match the initially published languages. Installed pairs are verified through the actual service and recorded in the architecture guide. The existing French machine draft is preserved unpublished; a French catalog does not imply an installed French model. Additional languages remain manual or require explicit model installation and capability refresh. Arabic, Simplified Chinese, Traditional Chinese, and other languages have registry and workflow support but are not published website catalogs.

Added dependencies are `next-intl` 4.14.9 for React/server message catalogs and ICU formatting, `@formatjs/icu-messageformat-parser` 3.5.21 for structural validation and protected message generation. Existing Next.js, React, Prisma, commerce, and payment dependencies were retained.

## Architecture

`lib/i18n/registry.ts` owns canonical BCP 47 identifiers, names, script direction, provider mappings, and the English default. `published.json` identifies complete bundled catalogs. Server publication merges this with cached `LocaleLanguage` metadata; proxy/layout reads project catalog-existence booleans and never load every language's JSON catalog. Incomplete, unreviewed, or outdated imported catalogs are not exposed to visitors. A separate `publicationOverride` flag records explicit administrator intent: refreshing provider capabilities cannot disable a bundled language. Only the active locale catalog is fetched, with a 30-second cache bounded to eight recently active catalogs and explicit invalidation after management writes. No provider calls occur during requests. Only the current language and relevant interface namespaces reach the browser.

Transient metadata read failures preserve the last successful publication snapshot, including administrator disables. A cold unknown/network failure produces a sanitized, negatively cached registry-unavailable error and the routing layer exposes English only; it does not guess that disabled bundled languages are published. A confirmed missing additive table permits bundled startup when no override snapshot exists. Explicit management invalidation discards old snapshots because publication may have changed. Imported locale routes also verify that their active catalog can actually be read before exposing that locale.

The additive Prisma migration adds `User.preferredLocale`, `LocaleLanguage`, `ContentTranslation`, and `TranslationJob`. Canonical product/category/brand/manufacturer/banner fields remain unchanged. Public reads batch stored translation lookups, verify source/context hashes, and preserve original values with an availability notice and source-language attributes when translations are missing. Unknown source scripts are identified as `und`, not labelled English. Product codes, financial amounts, stock, orders, customer data, and private messages are excluded from translation.

The LibreTranslate adapter implements the existing provider-independent interface using only the official self-hosted API. `/languages` reports exact directed `targets`; source and target names alone do not establish a pair. The observed capability snapshot is persisted transactionally, and each executed provider request also validates current pairs. Available models, prepared catalogs and published visitor languages remain independent. No provider calls occur during page rendering.

Native Python-venv setup, model candidates, verified installed pairs, and environment settings are documented in [translation-local-setup.md](translation-local-setup.md). The separate [isolated deployment guide](deployment.md) is prepared for a later phase. No production VPS was accessed or modified. See [translation-architecture.md](translation-architecture.md) for the inspection, file inventory, removed provider components, database changes, verification and limitations.

## Deployment

Install dependencies, apply the additive migration with the deployment database credentials, and generate the client. Prisma 7 reads deployment environment variables through `prisma.config.ts`; `DIRECT_URL` bypasses a pooled connection for migration locks.

```sh
npm ci
npx prisma migrate deploy
npx prisma generate
npm run build
npm run start
```

The migration has not been applied to an external database automatically. Do not reset the database. Use the normal deployment environment or an approved staging database for migration verification.

The only automatic provider is the native local LibreTranslate service. The TypeScript provider and native scripts default to `http://127.0.0.1:5001` because port 5000 belongs to the observed macOS Control Center/AirPlay service. Export `LIBRETRANSLATE_URL=http://127.0.0.1:5001` explicitly for the application, worker and CLI so existing environment files cannot select a different service. The scripts bind only to `127.0.0.1`. No API key is required for this loopback setup. `tools/libretranslate/.env.example` lists repository-script settings and the server URL; the complete application settings are in the local setup guide. Keep overrides in your untracked local environment. Keep the application database local during this phase; the existing port-15432 SSH tunnel reaches production and was not used.

## Interface catalogs

Run the CLI with the `react-server` condition because it shares server-only repository modules. CLI local environment loading reads `.env` and `.env.local` without overriding existing process variables.

```sh
node --conditions=react-server --import tsx scripts/translations.ts audit
node --conditions=react-server --import tsx scripts/translations.ts validate --file ./translations/ar.json
node --conditions=react-server --import tsx scripts/translations.ts generate --locale ar
```

The Arabic commands below illustrate the extensible workflow, not the currently installed model set. Executed Arabic generation first requires reviewed model/sentence pins in `tools/libretranslate/models.lock.json`, explicit model installation and an actual supported pair. The native default installs only en/bn. `generate` defaults to dry-run and reports message, fragment, and character counts without calling the provider. Generation sends translatable literal spans only: ICU expressions, rich-text tags, protected brands/codes, numeric values, URLs and variables stay local and are reassembled afterward. Long prose is split at whitespace into bounded requests. To explicitly authorize a bounded local generation after reviewing the workload:

```sh
node --conditions=react-server --import tsx scripts/translations.ts generate --locale ar --execute --max-characters 150000 --output ./translations/ar.json
```

Review the generated translations, including legal and privacy messages, before import/publication. Structural validation proves completeness and placeholder integrity; it does not prove linguistic accuracy or constitute human/legal review. Non-English imports/publication reject catalogs whose literal wording is wholly unchanged English, ignoring case, punctuation, whitespace, and ICU formatting. Equal protected brands and terms are allowed within a catalog that contains genuine changed messages; unchanged English regional variants are allowed. This deterministic guard does not establish adequate linguistic coverage: the named reviewer must verify translation quality and completeness. Meaningful unchanged messages are reported by key and require a separate intentional-shared-wording acknowledgement before catalog approval. The source English catalog is repository-controlled and cannot be replaced through administrator imports.

```sh
node --conditions=react-server --import tsx scripts/translations.ts import --locale ar --name Arabic --native-name العربية --file ./translations/ar.json --reviewed --reviewer operator-id --acknowledge-unchanged
node --conditions=react-server --import tsx scripts/translations.ts publish --locale ar --reviewer operator-id
node --conditions=react-server --import tsx scripts/translations.ts export --locale ar --output ./translations/ar-export.json
node --conditions=react-server --import tsx scripts/translations.ts unpublish --locale ar --reviewer operator-id
```

The existing authorized admin area at `/en/admin/translations` offers equivalent validated import/export, explicit review, enable/disable, content editing, controlled batches, failures, and retry controls. The API requires a current administrator role from the existing authorization guard, rejects cross-origin writes, validates request shapes, and limits import body size. English cannot be disabled. The CLI is an operator tool; its filesystem and database credentials require the existing deployment access controls.

Changing source interface catalogs changes their hash. Revalidate, review, and reimport affected language catalogs before republishing. Additional languages use the same namespaces and shared components; no component edits are needed. Compatible fallbacks share both a base language and writing system: French Canadian may fall back to French, while French cannot fall back to English and Simplified/Traditional Chinese remain distinct. Public snapshots resolve the requested translation, then an explicitly declared, currently published compatible fallback, then original source content. `fieldLocales` records the actual language rendered. A compatible fallback may make `contentAvailable` true while `translationAvailable` remains false; fallback-only page variants are not advertised as fully translated through SEO.

## Dynamic public content

Discover provider capabilities explicitly; this request does not translate public content:

```sh
node --conditions=react-server --import tsx scripts/translations.ts sync-provider
node --conditions=react-server --import tsx scripts/translations.ts status
```

A batch file contains only approved public entity identifiers and fields:

```json
{
  "entityType": "product",
  "entityIds": ["public-product-id"],
  "fields": ["name", "description", "descriptionBlocks", "seoTitle", "metaDescription"],
  "targetLocale": "bn",
  "sourceLocale": "en"
}
```

```sh
node --conditions=react-server --import tsx scripts/translations.ts batch --file ./translations/batch.json
node --conditions=react-server --import tsx scripts/translations.ts batch --file ./translations/batch.json --execute
node --conditions=react-server --import tsx scripts/translations.ts run --limit 5 --reviewer operator-id
```

The first command is a workload preview. The second queues a bounded batch and the third processes up to five jobs. Jobs execute sequentially per worker; serializable database claims enforce the global `TRANSLATION_CONCURRENCY` permit limit and deduplicate workers for the same source revision/context. No database transaction is held during provider HTTP calls. Serialization conflicts have a bounded retry, then return busy without a provider call. Each provider request has a timeout; workers renew leases every 30 seconds and guard writes with current ownership. The worker applies at most three automatic job attempts with backoff. Authorized explicit retries recover exhausted failures; a separate CLI worker polls the queue outside page rendering. Interrupted running jobs can be retried by an administrator after a ten-minute lease. Job records expose characters, attempts, status, and sanitized failures.

Machine output is stored as a draft, then reviewed and published in the admin area. Manual edits and explicitly reviewed machine translations become protected overrides and are never overwritten by automatic regeneration. Source changes mark approved wording stale for explicit review; unreviewed stale machine drafts queue bounded replacement jobs. Source mutations schedule staleness checks and bounded draft jobs through Next.js `after`; every public/SEO read also verifies the current source and context, so stale or obsolete jobs cannot be served as published content even if post-response work was interrupted. Manual stale translations require explicit review against the new source.

Approved fields are centralized in `lib/translations/content.ts`. Brand/manufacturer names, SKUs, model numbers, URLs, numeric technical values, and configured terms are protected. Structured product descriptions translate text nodes, headings, feature labels, alt text, and specification labels, preserving JSON structure, links, and technical specification values. Legacy raw HTML requires a reviewed structural migration/manual workflow; it is not automatically translated as plain text. No arbitrary model, private field, or free-form public translation endpoint exists.

Provider preparation can target every language returned by the official capability endpoint. Manual imports support valid additional BCP 47 identifiers independently. No provider-supported count is asserted until the capabilities refresh succeeds. `status` reports actual persisted counts; `audit` reports bundled catalog completeness. Runtime enabling/disabling is visible after cache expiry; admin writes clear the local cache immediately. Multi-instance deployments share the database and converge within 30 seconds.

## Verification and remaining review

Deterministic tests cover ICU placeholders/pluralization, language/script mapping, protected tokens, structural markup, workload previews, invalid configuration, private-field rejection, concurrent claims, obsolete sources, manual override protection, bounded retries, and administrator authorization/origin defenses. Run the normal repository lint, type-check, tests, and production build in addition to `scripts/check-i18n.ts` and the catalog audit.

Current local implementation verification is recorded in [translation-architecture.md](translation-architecture.md). Native installation, Python virtual-environment identity, real pair/translation responses, isolated PostgreSQL migrations, persisted draft/review/manual override behavior and outage reads have their own recorded evidence there. Earlier application checks are labelled separately when they predate native installation. Production database/VPS changes remain a separate phase.

Representative Arabic, Chinese, and longer-text languages must be imported, reviewed, and published before they can be offered to visitors. Dynamic translations and multilingual search quality depend on real catalog preparation. Searching translated terminology is not backed by a separate translated search index; existing catalog search still uses the canonical search implementation. This feature does not change financial calculations, delivery rules, payment integrations, or customer data.

The existing legal pages retain their original English contract text with explicit `lang="en"`/`dir="ltr"` and a translated availability notice. Their non-English variants remain unindexed until separately reviewed legal translations are implemented. Existing PDF invoices/reports also remain explicitly English: the current Helvetica/jsPDF templates do not embed Bengali/Arabic fonts or perform complex-script shaping. Their download labels identify English rather than advertising documents that cannot render the requested script. External EmailJS templates are hosted outside this repository and were neither modified nor sent during implementation.

Browser checks exercised the actual English and Bengali desktop/mobile selectors, equivalent contact URLs with query/fragment, persistent choice, authentication/wishlist preservation, safe draft recovery, and narrow mobile layout. Unpublished layout stress samples using the application's stylesheet exercised Arabic RTL, distinct Simplified/Traditional Chinese identifiers, and longer German labels; these were layout fixtures, not proof of complete translated production catalogs. Browser extensions added unrelated hydration attributes in the development browser; no application workaround suppresses these diagnostics. Human linguistic/legal review is still required for newly generated catalogs; actual local LibreTranslate validation is recorded in the linked setup guide.

The existing application-owned order-status notification builder uses whole ICU subject/body templates and all 13 status labels/descriptions in `notifications-en.json` and `notifications-bn.json`. Private recipient names, addresses, contacts, and order codes never go to the translation provider: formatting and interpolation are local. Signed-in order recipients use their valid published account preference through a best-effort lookup; missing profile/migration/catalog data falls back to English. Guest notifications default to English until a future order-language snapshot is available. The existing notification sink logs only; no actual email/SMS delivery provider is present or claimed. Validated imported catalogs can be passed to the pure builder for future delivery integrations. Notification namespaces are excluded from storefront browser payloads.
